# jirallm: staying-current

## Staying current

`jirallm watch` re-exports exported tickets and Confluence pages that changed since their local copy, plus open tickets assigned to me that are not exported yet and exported Slack threads with new replies (when Slack is set up; every 5 minutes at most, threads quiet for 14 days are skipped), and appends one line per change to `jira-export/CHANGES.md` (e.g. `ZOD-1: status: To Do → In Progress; Comments changed`). `jirallm changes` prints them compactly (one line per ticket, latest state); `--dry-run` on `watch` only lists what would be re-exported. A session-start hook running `jirallm changes --unseen --session <id>` puts new changes in context automatically, and a prompt hook does the same on each user message when `watch` logged something since; each Claude Code session keeps its own seen marker (`jira-export/.changes.seen.d/<id>`), so every open session gets every change, and the user sees a "📥 jirallm #N: N changes added to Claude's context" line when they arrive. Every report handed to a session starts with "[jirallm delivery #N · prompt|start|monitor HH:MM]" and is logged in `.changes.seen.d/<id>.log`; the plugin's PostToolUse/Stop hooks mark it read once Claude acts after it (next tool call or end of turn) (automatic: don't mention or acknowledge the number). The user follows deliveries per session in `jirallm ui` ("Claude sessions"). `jirallm status-line` (set as Claude Code's `statusLine` command) shows the last `watch` run, the last delivery and whether it was read ("📥 #3 11:30 PR #12 → ✓ read 11:31"), changes to the session's tickets still waiting ("⏳ 1 waiting for Claude"), and other tickets' changes ("+2 other"); `jirallm changes --log [--session <id>]` lists every delivery with its read state. `--install 15` runs it every 15 minutes in the background (`--uninstall` removes it).

Slack threads and Confluence pages linked in a prompt are followed by that session like its tickets (their new replies and versions are pushed to it). After a reboot, `jirallm resume` lists the Claude Code sessions left open (the plugin marks a session open until the user ends it with /exit, /clear or logout) and `jirallm resume <id>` reopens one unless it still runs; the plugin keeps `.vscode/tasks.json` of the workspace current (`jirallm resume --vscode <workspace>`), so opening the folder in VS Code starts one terminal per session. `--forget` drops a session from them. The Resume button in `jirallm ui` opens a session in a VS Code terminal (through the small jirallm sessions extension it installs on first use; VS Code asks once to allow its link), else in a terminal window.

Keeping `jira-export` lean: `watch` re-checks every exported ticket and page, so finished tickets are dead weight there and in searches. `jirallm prune --dry-run` lists the exports of tickets in the Done status category (Resolved, Rejected, …) and the Confluence pages only they link to, with sizes; `jirallm prune --yes` removes them. The user's own files in those folders (context.md, test reports, notes) are always kept. Pages exported on their own and Slack/SharePoint exports are not touched, and anything removed comes back with `jirallm <KEY>`. Use `--done-for <days>` to keep recently finished tickets and `--keep <keys>` for ones still being discussed. Suggest it when the folder grows large or many exported tickets are finished, and ask before running it with `--yes`.

Changes are focused per session on the tickets it works on (the keys its prompts named). The Claude Code plugin's background monitor "jirallm-changes" (every interactive session, not with `-p`) pushes a notification mid-session only for those tickets: CI failed or went green on their PR, a review or thread awaiting me, the ticket or a Slack thread about it moved. A session not on a ticket yet is never interrupted. Changes to other tickets arrive with the next prompt as one line of names ("Other changes, not this session's tickets: …"): don't act on them or investigate them; mention them only if the user asks (`jirallm changes` lists them). Without the plugin (or if the monitor reports no handshake), start `jirallm changes --follow --session <id> --output-dir <workspace>/jira-export` under the **Monitor** tool instead (`timeout_ms` 1800000, re-arm on expiry); the session-start context gives the exact command. Always pass `--session`: without it the shared marker is used. On an event for this session's ticket: CI failure on its PR → `jirallm pr-status --repo <worktree>` and fix it (ask before pushing); review/thread awaiting me → read and propose fixes or answers; Jira/Slack changes → mention briefly when they touch the current work. Not useful without the scheduled `watch` (check with `schtasks /Query /TN "jirallm watch"`).
